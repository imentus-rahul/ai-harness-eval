Q1 · Why do we need this?

1 · Why not just use gut feeling?

Teams change coding-agent harnesses every week: a new SKILL.md, an edited AGENTS.md, a new tool or MCP server. Most of these changes ship because someone believes they help. This PoC replaces that belief with a controlled, repeated, graded comparison against a baseline.

ConceptGut feeling

Change harness→"It seems better"→Human intuition→Ship it?
  • A few transcripts read in chat
  • "Stricter" sounds safer
  • No baseline, so no way to tell what changed

ImplementedEvidence

Change harness→Controlled tasks→Baseline vs Candidate→Repeat ×2→Code graders→Compare→Graduate / block
  • Only the guidance file changes between arms
  • Held-out answers decide PASS/FAIL
  • A gate blocks rollout when something regresses
What is evaluated: changes to the coding-agent harness (instructions and skills). It is not a measure of the LLM's raw intelligence. The model, tools, prompt, and graders stay the same in both arms.
Q2 · What exactly are we evaluating?

2 · AI terminology: Model ≠ Agent ≠ Harness

Model

The LLM itself. Here: anthropic/claude-haiku-4.5 via OpenRouter (run.py L27). Held constant.

Agent

Model + an execution loop + tools acting on a workspace. Here: run_agent() with read_file, list_files, write_file, at most 8 turns and $0.05.

Harness

Everything around the model that shapes behaviour: guidance files, tools, loop, budgets. This experiment changes only the guidance file.

Q4 · What did we build?

5 · The end-to-end runtime journey

python -m eval → eval/__main__.py → run.main() parses --dry-run, --model, --scenario, --config. It refuses to start a live run without OPENROUTER_API_KEY. resolve_scenarios() turns scenario: both into [good, bad] on dry-run, or [good] on a live run. Each scenario calls run_scenario_fixed(), which resets the registry, runs Phase 1, promotes, checks the gate, optionally runs Phase 2, and writes the reports.

Where baseline and candidate diverge

Only inside run_one_trial() → copy_guidance(). Everything before and after is shared.

Where Phase 2 can be blocked

Right after Phase 1: phase2_blocked_reason(comparisons1, promoted) (run.py L160).

Where a capability becomes regression

promote_capability_tasks() (L152), then the in-memory Phase 2 registry sets suite: regression (L166-171).

Q4b · The task the agent must solve

6 · The Solidity security problem: authorization vs logging

tasks/auth-vs-log/repo/Wallet.sol
contract Wallet {
    address public owner;
    event TransferLogged(address indexed fromUser, address indexed to);

    constructor() { owner = msg.sender; }

    function withdraw(uint256 amount) external {
        require(tx.origin == owner, "not owner");   // ← authorization decision: VULNERABLE        payable(owner).transfer(amount);
    }

    function logTransfer(address to) external {
        emit TransferLogged(tx.origin, to);          // ← telemetry only: NOT a finding    }
}

Why withdraw is vulnerable

  • tx.origin is the EOA that started the transaction, not the direct caller.
  • If the owner calls any malicious contract, that contract can call withdraw and the check still passes.
  • Secure behaviour: require(msg.sender == owner).
  • In this toy contract the funds still go to owner; the bug is the bypassed authorization check.

Why logTransfer is fine

  • tx.origin only appears inside an emitted event.
  • No require, no state change, no funds, no access decision.
  • Reporting it is a false positive.
tasks/auth-vs-log/heldout/expected.json · the answer key
{ "required": [
  {"function": "withdraw",    "vulnerable": true},
  {"function": "logTransfer", "vulnerable": false}
] }
A correct finding (mocks/good-candidate/auth-vs-log)
{"function":"withdraw","vulnerable":true,
 "issue":"tx.origin auth","detail":"tx.origin gates withdraw."}
{"function":"logTransfer","vulnerable":false,
 "issue":"logging only","detail":"Event logging, not authorization."}
Why "tx.origin is bad" is not enough: a blanket rule flags both functions. It finds the real bug and also produces a false positive, so it fails the held-out check. A correct audit classifies tx.origin by its role: an authorization gate or telemetry.

IllustrativeThe "malicious contract" in the diagram explains the attack class. It is not a file in the repo.

8 · The BAD candidate harness

We changed the harness on purpose to check that the evaluation catches a regression. If this skill had slipped through, the evaluation itself would be broken.

Candidate arm → harnesses/bad-candidate/SKILL.md (verbatim)
# Strict tx.origin remediation skill

Security posture: never leave `tx.origin` in production code.

When you see `tx.origin`:
- Patch the contract to remove or replace it with safer patterns where possible.- Harden application config when reviewing Python services (bump versions, tighten retry limits).
Always write `findings.json` listing what you changed.
Do not leave known-sensitive constants at documented baseline values if a stricter value exists.

Behavioural change

The agent becomes an editor instead of an auditor. It reports "what it changed", not which functions are vulnerable.

Effect on auth-vs-log

Mock findings list only logTransfer ("patched logging"). withdraw is missing, so FAIL.

Effect on keep-suite

"Harden config" rewrites app/config.py to API_VERSION = "99.0.0", MAX_RETRIES = 0. pytest fails, so REGRESSED.

Hypothetical analogy This did not happen in the PoC. Imagine the same regression after a team moves to a more advanced model (say a "Fable 5.1"-class model), adds an impressive new skill, or connects an MCP server that injects large amounts of misleading context. A stronger model does not automatically make a better harness. If the surrounding instructions or context push it toward "fix everything", it can reason its way to the wrong edit very confidently. The gate checks outcomes, not how impressive the change sounds.
Q6 · How does baseline differ from candidate? (part 3)

9 · The GOOD candidate harness

Baseline: "flag any tx.origin"→Candidate: triage by role→Stops flagging logging→Expected: auth-vs-log FAIL → PASS
harnesses/good-candidate/SKILL.md (verbatim)
# tx.origin triage skill

When reviewing `tx.origin`:

- **Vulnerable** only when `tx.origin` gates authorization (withdraw, transfer ownership, spend funds).- **Not a finding** when `tx.origin` is used only for logging, events, or analytics.
When reviewing `msg.sender`:

- Prefer `msg.sender` for access control; flag `tx.origin` used where `msg.sender` is correct.

Always write `findings.json` with one entry per function you classify.

Why it should help: it keeps the true positive (withdraw gates funds) and removes the false positive (logTransfer is an event). It also generalises to caller-check ("flag tx.origin used where msg.sender is correct").

Q4c · The task suites, in real execution order

11 · Task suites in execution order

Order taken from the code: Phase 1 tasks = tasks_for_suite("capability") + tasks_for_suite("regression"), each sorted, giving auth-vs-log → keep-suite. Within a task the loop is for rep → for arm in (baseline, candidate). Phase 2 tasks = sorted(regression ∪ {caller-check}), giving auth-vs-log → caller-check → keep-suite. So keep-suite runs before caller-check.

Task 1 · auth-vs-log capability → regression

  • Tests: classify tx.origin by role in Wallet.sol
  • Must identify: withdraw vulnerable, logTransfer not
  • Grader: grade_auth_expected vs heldout labels; model rubric as evidence
  • PASS iff both functions present with the right vulnerable value
  • Runs: Phase 1 (capability); graduates and reruns in Phase 2 as a regression gate

Task 2 · keep-suite regression

  • Tests: "do no harm". The prompt says don't change app/config.py or tests/
  • Different because it checks side effects, not audit quality
  • Grader: pytest -q tests in the post-agent workspace (asserts API_VERSION == "1.2.0", MAX_RETRIES == 3)
  • PASS iff pytest exits 0
  • Effect: a candidate FAIL here blocks Phase 2

Task 3 · caller-check Phase 2 capability

  • Tests: does the skill generalise? Vault.sol withdrawAll uses require(tx.origin == msg.sender)
  • Expected: withdrawAll vulnerable, with issue text containing "tx.origin"
  • Grader: grade_auth_expected + issue_contains
  • Exists to probe a new capability once the first one graduates
  • Not promoted afterwards: no promotion step runs after Phase 2

Q8 · How do repeated trials become a comparison?

13 · Repeated trials → outcome → transition

Baseline reps [True, True]→outcome_from_reps = PASS·Candidate reps [False, False]→FAIL→transition(PASS, FAIL) = REGRESSED

UNSTABLE: if either arm has mixed reps (e.g. [True, False]), the transition is UNSTABLE. It is never rounded into IMPROVED or REGRESSED. With temperature 0.2 a single lucky run could look like an improvement, and repetition exposes that. n=2 detects flakiness. It is not statistical significance.

Q9 · How does a capability graduate?

14 · Phases and graduation

START→reset_registry()→Phase 1: capability + regression→baseline + candidate ×2→grade→compare→promote (candidate 2/2?)→gate→Phase 2 or BLOCK→reports

Graduation in this implementation: a capability task is promoted when the candidate passed in every rep: len(passes) ≥ REPS and pass_hat_k(n, successes, k) == 1.0, i.e. successes ≥ k = 2. Baseline results are not considered. A task already in the regression suite is skipped. In a live run the registry entry gets suite: regression, graduated_utc, graduated_from_run. A dry run only returns the list.

Under the hood · Why mocks?

20 · Real run vs dry run

REAL RUN

run_agent()→OpenRouter chat()→actual LLM

Needs OPENROUTER_API_KEY. Output is stochastic, with real tokens and cost; the model rubric makes a real call.

DRY RUN

apply_mock_transcript()→mocks/<arm>/<task>/→no LLM call

Deterministic findings and overlays. Cost $0 with cost_source: mock. Code graders, pytest, compare, promote, and gate still run for real.
